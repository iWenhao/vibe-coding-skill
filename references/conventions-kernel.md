# 约定内核（栈无关）

本文件是 `AGENTS.md` 骨架各节背后的**理由与完整规则**。scaffold 生成的模板只写结论，需要判断边界时来查这里。

判断一条约定值不值得进新仓库，问一句：**这条是仓库属性（任何机器、任何 agent 都成立），还是原项目/原机器的偶然事实？** 前者搬，后者只搬写法。

---

## 1. 文档地图，不是单份大文档

四份各有读者，互相引用而不重复内容：

| 文件 | 读者 | 回答 |
| --- | --- | --- |
| `README.md` | 第一次打开仓库的人 | 这是什么、架构、目录、快速开始 |
| `AGENTS.md` | AI 代理 / 新接手的人 | 怎么在这仓库干活：命令、约定、坑、扩展点 |
| `docs/USER_GUIDE.md` | 使用者 | 功能怎么操作 |
| `CHANGELOG.md` | 想知道改动来由的人 | 为什么改、动了哪些文件、实测了什么 |

分工规则（最容易写错的一条）：**提交标题只回答「改了什么」，理由、文件清单、实测数据、边界情况全部写进 CHANGELOG**。同一件事实不在两处各写一遍。

`AGENTS.md` 顶部放一行「文档地图」列出上面几份并说明各自职责；有「触发即必读」的专项规范（如图元绘制、设计系统）也在这行列出，条件写清楚。

## 2. 常用命令

只列命令与端口，**门槛与检查取舍指向「验证节奏」一节，此处不重复**。额外保留一条最高优先级例外，写在命令节末尾：

> 用户可见的输出（UI / 控制台 / 日志格式）必须真跑一次看结果，优先级高于全部静态检查。

原因见第 8 节——有一类 bug 单测与类型检查全绿但屏幕上是乱码。

## 3. 环境与已知坑

写法见 [pitfalls.md](pitfalls.md)。要点：仓库属性直接写；绑定某台机器的条目前缀 `〔本机〕`，并注明「换机器或 CI 上不适用，不要照搬」。

## 4. 任务清单与进度可见性

写进 AGENTS.md 时面向**任何 agent**，不能依赖某一次对话里的口头说明：

- 多步任务必须有一份**对用户可见**的进度清单：开工前列出、过程中更新、收尾给出最终状态。只在内部维护而不展示，等于没做。
- **第一步先自查环境有没有原生清单能力**（判据是「这一轮有没有 list / todo 类工具」，不是具体工具名——名字会随实现变化）。有就直接用；没有则手写文字版清单，**开工第一条与收尾最后一条消息各附一份**，状态标记固定 `✅ 已完成 / 🔄 进行中 / ⬜ 未开始`，且要一眼看出哪些没做，不要只汇报做完的部分。
- **清单不等于事实**：它不会自动跟着现实更新。收尾时必须对着 `git status` 与测试结果重新核一遍——已发生过「清单显示全部未开始、而代码早已提交」。

## 5. 工作流约定

### 分支与粒度

日常开发提交到 `dev` 并推送 `origin dev`，`master` 用于发布合并。一个功能/修复一个提交。新项目可换别的分支模型，但**必须在 AGENTS.md 里写死一种**，别让 agent 每次推断。

### 提交信息

格式 `前缀: 说明`，首行 ≤ **30 字符**（按 Unicode 码点计，一个汉字算 1，不是显示列）。

前缀白名单：`功能` `修复` `优化` `重构` `清理` `文档` `测试` `构建` `发版`。Git 自动生成的 `Merge` / `Revert` / `fixup!` / `squash!` 不受限。

读者是 `git log --oneline`，不是代码评审——所以标题只回答「改了什么」。合规示例：`修复: 亮色主题下画布背景仍是黑色`（17 字符，实测码点数；同一串按 UTF-8 字节算是 47）；把整段设计说明塞进标题一定会超。

**必须机械拦截**：`scripts/commit-msg-check.mjs` + `scripts/hooks/commit-msg`，超长或未知前缀直接拒绝提交。每个克隆启用一次 `git config core.hooksPath scripts/hooks`；确需绕过用 `git commit --no-verify`。

为什么逻辑放 Node 而不是 shell：shell 的 `${#var}` 与 `wc -c` 在 UTF-8 下按**字节**算，中文标题会被算成 3 倍而全部误判。这也是把校验做成独立脚本（而非内联在钩子里）的原因——可单测、可跨平台。

### 变更日志

`CHANGELOG.md` 用 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/) 格式，头部写清版本规则与本文件的定位（详略分工见第 1 节）。功能与修复类提交同步更新 `[Unreleased]` 区。

条目的写法不是「动了哪个函数」，而是**动因 + 做了什么 + 实测**：

- 动因：谁提出的、原来哪里别扭（用户视角，不是代码视角）；
- 做法：关键设计与**为什么这样取舍**，尤其「为什么不是另一种实现」；
- 实测：新增几个用例、跑了哪些检查、全量数字。

### 版本号

从 `0.0.1` 起步，末位每次 +1，满 10 进位（`0.0.9 → 0.0.10 → 0.1.0`）。发版时版本号后附当天日期 YYMMDD（如 `0.0.2-260928`，CHANGELOG 标题与 tag 使用），`package.json` 保留三段数字并同步。

**时机比规则更重要**：版本号只在用户明确说「发版」时更新；平时提交一律不动版本号，新内容只写 `[Unreleased]`。这条不写进 AGENTS.md，agent 会在每次提交时制造无意义的版本变更。

### 不提交什么

`node_modules/`、构建产物、诊断用的临时代码。另外必须显式列进 `.gitignore` 的高频误入项：运行时数据目录、agent 本地配置目录、临时构建产物。`git add -A` 前扫一眼暂存区。

### UI 交互约定（有界面的项目）

- **新功能必须有可见 UI 入口**——只有快捷键没有按钮等同没做。
- 次级操作图标默认隐藏、悬停显示或收进「⋯ 更多」菜单；主按钮放显眼位置（如面板标题右侧）。
- 不做视觉冗余的堆砌。标准是普通用户「看得到、找得到、用得顺」。

## 6. 代码风格

- **注释用中文，说明「为什么」而非「做了什么」**。默认不写注释：只有当理由非显而易见（隐藏约束、微妙不变量、针对具体 bug 的 workaround、会让读者意外的行为）才写。删掉它也不会让后来人困惑的注释，就不要写。
- **类型严格模式四件套**：`strict` + `noUnusedLocals` + `noUnusedParameters` + `noFallthroughCasesInSwitch`。未使用的变量/参数会挂构建，所以事件参数不用时改名 `_e`。这是「让错误在构建期而不是运行时暴露」的最低成本配置，任何 TS 项目都该开。
- **分层约定**：状态管理只放跨组件状态；单文件内的复杂逻辑抽 composable / hook，**新逻辑写进对应模块而不是往主文件里堆**。可纯函数化的算法独立成文件并配测试。
- **持久化走抽象层，不要直接调底层 API**（`localStorage` / 文件系统 / DB）：一个 `getStorage()` 类的入口，便于加远程后端与降级。
- **服务端/后端代码改动必须加中文注释**：模块职责、接口约定、安全与兼容注意点，风格对齐既有文件。前端容易靠读代码理解，后端的路由与数据格式没有注释会被反复误改。

### 防重复：先找现成的，三次必收敛

- 写新逻辑前先搜仓库有没有现成实现（工具函数、展示映射、共享逻辑模块），有就复用，不要复制一份改改。
- **同一段逻辑第三次出现必须抽公共模块**——宁可当场花十分钟收敛，也不要留下第四份。错误的抽象比重复更贵，但重复放任不管就是债。
- 公共实现保持单一来源，扩展时复用而非另写平行实现。值得预置的公共入口（新仓库一开始就该有，别等到第四份复制）：ID 生成、状态→文案/样式映射、剪贴板/复制粘贴、同类客户端的基类、存储键、结构化读写工具。
- 发版前跑一遍重复扫描体检（如 `npx jscpd src server --min-tokens 60`），重复率明显上升或出现成段克隆时当次收敛。

### 文件超长时自动拆分（不要等积重难返）

阈值：单文件（组件/逻辑/服务端）**> 400 行**、样式 **> 500 行**。拆法：按区块拆子组件、样式外置、逻辑抽 composable、服务端按域拆模块。拆完必须类型检查 + 测试通过且行为不变。

**例外**：数据/图标定义类长文件（内容随业务条目线性增长，拆开只是搬运）可豁免，但豁免必须**写进检查脚本的参数**并在输出末尾报出跳过数量——例外必须可见，不能变成静默豁免。

### 收尾硬性检查

准备提交前必须统计源码文件行数，发现超阈值文件**当次拆完再提交**，禁止「先提交超长文件以后再拆」。这条只针对**本次新增或触及的文件**；历史欠账不阻塞无关提交，但**必须在当次汇报里如实列出**，不许默默略过。

```bash
node scripts/check-long-files.mjs          # 默认扫约定目录，超限则退出码 1
node scripts/check-long-files.mjs --roots src,server --exclude "src/industrial/*"
```

计行必须与行尾风格无关（仓库内 CRLF/LF 混用是常态）：读全文后按 `/\r?\n/` 切、丢掉末尾空元素。踩过的坑：`(Get-Content | Measure-Object -Line).Lines` 不计空行、对纯 LF 文件漏得更多，会让接近阈值的文件静默通过。

## 7. 架构与扩展点（每仓库特有，必须人工填）

这一节是 AGENTS.md 里唯一**不能靠模板生成**的部分，也是价值最高的部分。写法模板：

> 要做 X 这类改动时：① 照 `<某个具体文件:行>` 的格式写；② 在 `<注册点>` 注册；③ 补 `<模拟数据/测试/文档>`；④ 同步 `<文档清单>`。

要点：给**可抄的样板文件路径**，给**步骤序号**，给**必须同步的位置清单**。抽象描述（「遵循现有模式」）对 agent 无效。

## 8. 验证节奏（按改动范围分级，不必每次全跑）

表格最后一行是**底线（唯一权威定义）**；过程中的检查按范围挑着跑——全跑一遍既慢又稀释信号。

| 改动情形 | 该跑什么 | 为什么 |
| --- | --- | --- |
| 迭代中（还没改完） | 只跑刚动的那个测试文件 | 全量慢，且中途失败多为半成品状态，噪声大于信息 |
| 改了后端/服务端代码 | 该侧的类型检查或编译 | 前端那套类型检查的 include 往往不覆盖服务端目录，不跑等于零把关 |
| 跨模块重构 / 改了类型签名与导出 | 全量类型检查 | 跨文件重构的错误类型检查最灵（`Record` 缺键、接口字段漏传这类单测看不出来） |
| 准备提交或交付 | 全量测试 + 类型检查 + 构建 + 行数检查 | 项目底线，不可跳过。构建覆盖类型检查看不见的静态资源与分包问题；行数检查测试与类型检查都抓不到 |
| 引入新文件或改动文件较多 | 加跑**改动文件**的 lint | 全量 lint 会被仓库既有报警淹没，信号被稀释 |
| 影响用户可见的输出（UI / 控制台 / 日志格式） | **必须真跑一次并看结果**，优先级排在上面全部之前 | 见下 |

**有一类 bug 静态检查抓不到：「渲染出来不对」**。真实案例——把 `.` 当背景在终端显示成一片圆点、拿字母当像素字符、中文按 1 列算导致信息栏错列：单测与类型检查全绿，用户看到的是一屏乱码。

配套两条实操：

- 起临时进程、截图这类重动作**只在最后一轮做一次**；启动前查端口占用，验证完务必关掉。
- 临时验证要和用户正在跑的实例**错开**：备用端口 + 临时数据目录，别动对方进程与数据；完事清理误建的目录与数据文件。

## 9. 测试

- 单测放**被测文件同目录**（`*.test.ts`），不集中放——测试与被测代码一起移动才不会漂。
- 新增核心逻辑时补同目录测试；UI 组件暂不强求。
- 需要打桩的场景：状态管理用「注入活跃实例」的官方写法；时间相关用假定时器；浏览器/网络 API（WebSocket、scroll、matchMedia）用 stub global。
- **UI 改动的浏览器实测套路**：原生拖放与画布内对象命中需要合成事件才能测（对画布容器合成 `contextmenu`/`dragover`/`drop`，坐标 = 容器 rect + 元素中心；被遮挡的按钮可程序化 `el.click()`）。
- 写进 CHANGELOG 的「实测用例数」必须来自**完整的一次运行**。如果运行环境会静默少跑文件（沙箱权限报错但汇总仍显示通过），判据是：汇总行出现 `Errors` 即视为本次不可信，需重定向临时目录后多轮全量 + 补跑，直到逐文件列表与磁盘上的测试文件清单比对一致。
