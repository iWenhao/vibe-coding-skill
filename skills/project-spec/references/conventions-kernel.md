# 约定内核（栈无关）

本文件是 `AGENTS.md` 骨架各节背后的**理由与完整规则**。scaffold 生成的模板只写结论，需要判断边界时来查这里。

判断一条约定值不值得进新仓库，问一句：**这条是仓库属性（任何机器、任何 agent 都成立），还是原项目/原机器的偶然事实？** 前者搬，后者只搬写法。

---

## 1. 文档地图，不是单份大文档

五份各有读者，互相引用而不重复内容：

| 文件 | 读者 | 回答 |
| --- | --- | --- |
| `README.md` | 第一次打开仓库的人 | 这是什么、架构、目录、快速开始 |
| `AGENTS.md` | AI 代理 / 新接手的人 | 怎么在这仓库干活：命令、约定、坑、扩展点 |
| `docs/USER_GUIDE.md` | 使用者 | 功能怎么操作 |
| `docs/WORKFLOW.md` | 正在发版 / 要开并行工作树的人 | 低频工作流细则：隔离方式怎么挑、版本号怎么进位与定稿 |
| `CHANGELOG.md` | 想知道改动来由的人 | 为什么改、动了哪些文件、实测了什么 |

分工规则（最容易写错的一条）：**提交标题只回答「改了什么」，理由、文件清单、实测数据、边界情况全部写进 CHANGELOG**。同一件事实不在两处各写一遍。

`AGENTS.md` 顶部放一行「文档地图」列出上面几份并说明各自职责；有「触发即必读」的专项规范（如设计系统、数据协议）也在这行列出，条件写清楚。

### 主文件有字节预算，不是行数预算

Codex 的 `project_doc_max_bytes` 默认 32 KiB，管的是**「项目根 → 当前工作目录」这条链上所有 AGENTS.md 合并后的总量**，拼到上限就停止加载更靠近工作目录的那份——**是整份进不来，不是尾部被裁**。其他工具各有各的上限，但结论一样：**按字节量，别按行数量**（中文 UTF-8 一个字占 3 字节，同样 200 行的中文仓库真实体积接近英文的三倍）。

由此定两条取舍：

- **留在主文件的判据**：每轮都要用的事实（命令、验证节奏、禁区、提交约定）。**能读代码自证的删**——这一刀通常能把说明书砍掉三分之一，剩下的全是 agent 推不出来的硬约束。
- **`AGENTS.md` 里的细则只能挪进同一仓库的 `docs/`**，**不能挪进本 Skill 的 `references/`**：references 属于 Skill，不随生成的仓库走，挪过去等于内容对新项目彻底消失。挪的时候必须在文档地图那行写清「什么时候必读」，否则等于删掉。
- **本 Skill 已外置的三块**（进 `docs/WORKFLOW.md`）：并行改动的隔离方式怎么选、版本号的进位与 YYMMDD 后缀、发版前的重复扫描。判据是「只在特定那一轮用得上，且干那一轮的人本来就会先查」。反面同样要守住：**每轮都得遵守的硬规矩必须留在主文件**——「绝不 `git add -A`」「平时提交不动版本号」这类挪走就会产生副作用，因为 agent 不会为一条它不知道存在的规则去翻文档。

`scripts/audit.mjs` 会按这份预算报字节数与占比（≥75% 提醒、超预算报缺失），所以体积是看得见的数字，不靠人感觉。

## 2. 常用命令

只列命令与端口，**门槛与检查取舍指向「验证节奏」一节，此处不重复**。额外保留一条最高优先级例外，写在命令节末尾：

> 用户可见的输出（UI / 控制台 / 日志格式）必须真跑一次看结果，优先级高于全部静态检查。

原因见第 8 节——有一类 bug 单测与类型检查全绿但屏幕上是乱码。

## 3. 环境与已知坑

写法见 [pitfalls.md](pitfalls.md)。要点：仓库属性直接写；绑定某台机器的条目前缀 `〔本机〕`，并注明「换机器或 CI 上不适用，不要照搬」。

## 4. 任务清单与进度可见性

写进 AGENTS.md 时面向**任何 agent**，不能依赖某一次对话里的口头说明：

- 多步任务必须有一份**对用户可见**的进度清单：开工前列出、过程中更新、收尾给出最终状态。只在内部维护而不展示，等于没做。
- **第一步先自查环境有没有原生清单能力**（判据是「这一轮有没有 list / todo 类工具」，不是具体工具名——名字会随实现变化）。有就直接用；没有则手写文字版清单，**开工第一条与收尾最后一条消息各附一份**，状态标记固定 `✅ 已完成 / 🔄 进行中 / ⬜ 未开始`，且要一眼看出哪些没做，不要只汇报做完的部分。
- **清单不等于事实**：它不会自动跟着现实更新。收尾时必须对着 `git status` 与测试结果重新核一遍——已发生过「清单显示全部未开始、而代码早已提交」。

## 5. 工作流约定

### 分支与粒度

日常开发提交到 `dev` 并推送 `origin dev`，`master` 用于发布合并。一个功能/修复一个提交。新项目可换别的分支模型，但**必须在 AGENTS.md 里写死一种**，别让 agent 每次推断。

### 并行改动（多个会话 / 多个 agent 同时动本仓库）

写进新仓库时分层落点：三条硬规矩（按模块分工、绝不 `git add -A`、开工先 `git status --short`）留 `AGENTS.md`，**隔离方式怎么挑与共享状态清单放 `docs/WORKFLOW.md`「并行改动隔离」**，主文件写明「要开工作树或多实例前先读它」。理由见第 1 节的字节预算。

先按环境能力挑隔离方式，再按范围分工。**判据顺序，能用上一层就不往下一层退**（判断「有没有原生能力」的依据同第 4 节：看你这一轮实际有哪些工具/参数，不要照抄别人的工具清单）：

1. **环境有原生工作树隔离**（派子任务时能指定「隔离的工作树」这类参数）→ 用它，通常还会自动清理没改动的副本。
2. **没有原生能力** → 手工开，就一条命令：

   ```bash
   git worktree add ../wt-<slug> -b wt/<slug> dev   # 新目录 + 新分支；dev 仍归主工作树正常检出
   ```

   进去后要单独装依赖——`node_modules/` 是被忽略的，不跟着工作树走。收尾 `git worktree remove ../wt-<slug>`（分支留着等合并），全清完再 `git worktree prune`。
3. **连独立目录都不方便**（同一个工作树里跑多个会话）→ 退化成三条硬规矩：按模块切分工（一个会话只碰前端目录，另一个只碰服务端）、**绝不 `git add -A` / `git commit -a`**（只 add 自己动过的文件）、开工先 `git status --short` 且把他人的改动原样留着不动。

**git 禁止同一个分支被两个工作树同时检出**（实测 git 2.45.1：对已检出的分支再 `git worktree add ../wt-probe dev` 报 `fatal: 'dev' is already used by worktree at '...'`，且失败后不留目录）。所以每个并行工作树必须各自 `-b` 新分支、最后逐层合回日常分支。这条拒得对：它把「两个会话都往日常分支提交、后推送的那个拿到 non-fast-forward」提前成开工当场就能看到的错误。

**工作树只隔离磁盘编辑与暂存区，两类东西它管不了**：

- **语义冲突**：两边用不同方式改同一个函数；`CHANGELOG.md` 的 `[Unreleased]` 每个人都在同一位置追加——这是**必然冲突点**，合并时按提交时间手工接，别指望 git 自动合对。
- **git 之外的共享状态**，凡是「进程或浏览器共用、不受 git 管」的都要逐个错开。最常见三处：运行时数据目录（两个后端实例指向同一个 `DATA_DIR` 就是跨进程竞态写同一批文件，并行实例一律自备 `DATA_DIR`）、端口（开发端口只归主工作树，并行用备用端口起）、正在被浏览器占用的登录会话与本地存储。这一条与第 8 节「临时验证要和用户正在跑的实例错开」是同一原则的两种场景。

为什么写成「顺序」而不是「一律用工作树」：实测的坑在第三层——同一工作树里并行时，`git add` 拿的是**当时整个工作树的快照**，会把他人的 WIP 一起卷进自己的提交。已发生过接近的情况：另一会话的 4 个文件在 `git status` 里与本次改动混在一起，靠提交完再 `git show --stat` 复核才确认它们没被带进去。所以第三层不是兜底摆设，它要求**每次提交前复核暂存区**（与第 5 节「`git add -A` 前扫一眼暂存区」是同一条）。

### 提交信息

格式 `前缀: 说明`，首行 ≤ **30 字符**（按 Unicode 码点计，一个汉字算 1，不是显示列）。

前缀白名单：`功能` `修复` `优化` `重构` `清理` `文档` `测试` `构建` `发版`。Git 自动生成的 `Merge` / `Revert` / `fixup!` / `squash!` 不受限。

读者是 `git log --oneline`，不是代码评审——所以标题只回答「改了什么」。合规示例：`修复: 亮色主题下画布背景仍是黑色`（17 字符，实测码点数；同一串按 UTF-8 字节算是 47）；把整段设计说明塞进标题一定会超。

**必须机械拦截**：`scripts/commit-msg-check.mjs` + `scripts/hooks/commit-msg`，超长或未知前缀直接拒绝提交。每个克隆启用一次 `git config core.hooksPath scripts/hooks`；确需绕过用 `git commit --no-verify`。

为什么逻辑放 Node 而不是 shell：shell 的 `${#var}` 与 `wc -c` 在 UTF-8 下按**字节**算，中文标题会被算成 3 倍而全部误判。这也是把校验做成独立脚本（而非内联在钩子里）的原因——可单测、可跨平台。

### 变更日志

`CHANGELOG.md` 用 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/) 格式，头部写清版本规则与本文件的定位（详略分工见第 1 节）。功能与修复类提交同步更新 `[Unreleased]` 区。

条目的写法不是「动了哪个函数」，而是**动因 + 做了什么 + 实测**：

- 动因：谁提出的、原来哪里别扭（用户视角，不是代码视角）；
- 做法：关键设计与**为什么这样取舍**，尤其「为什么不是另一种实现」；
- 实测：新增几个用例、跑了哪些检查、全量数字。

### README 同步（重要文件改动时）

文档地图里 README 回答「这是什么、怎么装、怎么跑」，全仓库最容易烂掉的就是它——`package.json` 换个脚本名、改个端口，README 的快速开始立刻变成谎言，而改代码的 agent 往往不觉得自己动了「文档该管的东西」。所以这条要做成机械拦截，不只靠自觉：

- **触发清单**：`scripts/commit-msg-check.mjs` 头部的 `DOC_SYNC_PATTERNS` 常量——默认 `package.json`、`pnpm-workspace.yaml`、`.env.example`、根目录 `*.config.*`、`tsconfig*`。这些文件决定 README 的「环境要求 / 快速开始 / 常用命令」是否还成立。清单按项目实际增删（monorepo 子包等），但增删要改常量，不要靠记性。
- **规则**：暂存区命中清单而 `README.md` 不在暂存区 → 钩子拒绝提交。正确做法是**同轮**更新 README 对应段落再提交，不要攒。
- **豁免必须可见**：确无需同步时，提交正文单独一行 `[skip-docs]`——标记随提交入库，`git log --grep skip-docs` 可审计；这与行数检查「例外必须写进参数并在输出里报出」是同一条原则，不允许静默豁免。`--no-verify` 是兜底而不是日常。
- **清单为什么不含 `src/**`**：「重大调整」没法机械判断，脚本只拦高置信子集；改 `src/**` 是否牵连 README（新功能入口、目录说明、交互方式）是判断题，由 AGENTS.md 的文字规约约束 agent 同轮自查——「能用脚本拦住的拦住，拦不住的写成规约」。

### 版本号

从 `0.0.1` 起步，末位每次 +1，满 10 进位（`0.0.9 → 0.0.10 → 0.1.0`）。发版时版本号后附当天日期 YYMMDD（如 `0.0.2-260928`，CHANGELOG 标题与 tag 使用），`package.json` 保留三段数字并同步。

**时机比规则更重要**：版本号只在用户明确说「发版」时更新；平时提交一律不动版本号，新内容只写 `[Unreleased]`。这条不写进 AGENTS.md，agent 会在每次提交时制造无意义的版本变更。

**落点分工**（别写成三处）：进位与 YYMMDD 后缀这类机制只写在生成仓库的 `docs/WORKFLOW.md`「发版与版本号」一处，`CHANGELOG.md` 头部与 `AGENTS.md` 各放一行指针——「时机」那条硬规矩留在 `AGENTS.md` 正文。

### 不提交什么

`node_modules/`、构建产物、诊断用的临时代码。另外必须显式列进 `.gitignore` 的高频误入项：运行时数据目录、agent 本地配置目录、临时构建产物。`git add -A` 前扫一眼暂存区。

### UI 交互约定（有界面的项目）

- **新功能必须有可见 UI 入口**——只有快捷键没有按钮等同没做。
- 次级操作图标默认隐藏、悬停显示或收进「⋯ 更多」菜单；主按钮放显眼位置（如面板标题右侧）。
- 不做视觉冗余的堆砌。标准是普通用户「看得到、找得到、用得顺」。

## 6. 代码风格

- **注释用中文，说明「为什么」而非「做了什么」**。默认不写注释：只有当理由非显而易见（隐藏约束、微妙不变量、针对具体 bug 的 workaround、会让读者意外的行为）才写。删掉它也不会让后来人困惑的注释，就不要写。
- **类型严格模式四件套**：`strict` + `noUnusedLocals` + `noUnusedParameters` + `noFallthroughCasesInSwitch`。未使用的变量/参数会挂构建，所以事件参数不用时改名 `_e`。这是「让错误在构建期而不是运行时暴露」的最低成本配置，任何 TS 项目都该开。
- **分层约定**：状态管理只放跨组件状态；单文件内的复杂逻辑抽 composable / hook，**新逻辑写进对应模块而不是往主文件里堆**。可纯函数化的算法独立成文件并配测试。
- **持久化走抽象层，不要直接调底层 API**（`localStorage` / 文件系统 / DB）：一个 `getStorage()` 类的入口，便于加远程后端与降级。
- **服务端/后端代码改动必须加中文注释**：模块职责、接口约定、安全与兼容注意点，风格对齐既有文件。前端容易靠读代码理解，后端的路由与数据格式没有注释会被反复误改。

### 防重复：先找现成的，三次必收敛

- 写新逻辑前先搜仓库有没有现成实现（工具函数、展示映射、共享逻辑模块），有就复用，不要复制一份改改。
- **同一段逻辑第三次出现必须抽公共模块**——宁可当场花十分钟收敛，也不要留下第四份。错误的抽象比重复更贵，但重复放任不管就是债。
- 公共实现保持单一来源，扩展时复用而非另写平行实现。值得预置的公共入口（新仓库一开始就该有，别等到第四份复制）：ID 生成、状态→文案/样式映射、剪贴板/复制粘贴、同类客户端的基类、存储键、结构化读写工具。
- 发版前跑一遍重复扫描体检（如 `npx jscpd src server --min-tokens 60`），重复率明显上升或出现成段克隆时当次收敛。

### 文件超长时自动拆分（不要等积重难返）

阈值：单文件（组件/逻辑/服务端）**> 400 行**、样式 **> 500 行**。拆法：按区块拆子组件、样式外置、逻辑抽 composable、服务端按域拆模块。拆完必须类型检查 + 测试通过且行为不变。

**例外**：数据/图标定义类长文件（内容随业务条目线性增长，拆开只是搬运）可豁免，但豁免必须**写进检查脚本的参数**并在输出末尾报出跳过数量——例外必须可见，不能变成静默豁免。

### 收尾硬性检查

准备提交前必须统计源码文件行数，发现超阈值文件**当次拆完再提交**，禁止「先提交超长文件以后再拆」。这条只针对**本次新增或触及的文件**；历史欠账不阻塞无关提交，但**必须在当次汇报里如实列出**，不许默默略过。

```bash
node scripts/check-long-files.mjs          # 默认扫约定目录，超限则退出码 1
node scripts/check-long-files.mjs --roots src,server --exclude "src/icons/*"
```

计行必须与行尾风格无关（仓库内 CRLF/LF 混用是常态）：读全文后按 `/\r?\n/` 切、丢掉末尾空元素。踩过的坑：`(Get-Content | Measure-Object -Line).Lines` 不计空行、对纯 LF 文件漏得更多，会让接近阈值的文件静默通过。

## 7. 架构与扩展点（每仓库特有，必须人工填）

这一节是 AGENTS.md 里唯一**不能靠模板生成**的部分，也是价值最高的部分。写法模板：

> 要做 X 这类改动时：① 照 `<某个具体文件:行>` 的格式写；② 在 `<注册点>` 注册；③ 补 `<模拟数据/测试/文档>`；④ 同步 `<文档清单>`。

要点：给**可抄的样板文件路径**，给**步骤序号**，给**必须同步的位置清单**。抽象描述（「遵循现有模式」）对 agent 无效。

## 8. 验证节奏（按改动范围分级，不必每次全跑）

**这一节要立的第一条规矩是「默认动作」：改完代码后跑的是受影响的测试，不是全量。** 光有分级表不够——agent 手上最容易滑回的动作就是「保险起见全跑一遍」。

为什么这条要写成硬约束而不是效率建议：在受限运行环境里，全量跑**回来的结果本身经常不可信**。运行器会被沙箱的临时目录权限打断，静默少跑若干测试文件（文件数在几个值之间来回跳），汇总行只要带 `Errors` 那次就等同于没跑过。付了一分钟，换回一个残缺的绿灯——比不跑更危险，因为它让人以为把关做过了。所以过程检查按嫌疑范围三选一即可：**单个文件/模块**、**受 git 改动影响的一批**、**几条特定用例**。具体开关名查本栈测试工具文档（Vue 栈的三条命令见 [stack-vue-ts.md](stack-vue-ts.md)），三个都接受路径子串模糊匹配、多个参数是「或」关系。

表格最后一行是**底线（唯一权威定义）**；过程中的检查按范围挑着跑——全跑一遍既慢又稀释信号。

| 改动情形 | 该跑什么 | 为什么 |
| --- | --- | --- |
| 迭代中（还没改完）——最常见 | 只跑刚动的那个测试文件，或「受改动影响」那一档 | 全量慢，且中途失败多为半成品状态，噪声大于信息 |
| 改了后端/服务端代码 | 该侧的类型检查或编译 | 前端那套类型检查的 include 往往不覆盖服务端目录，不跑等于零把关 |
| 跨模块重构 / 改了类型签名与导出 | 全量类型检查 | 跨文件重构的错误类型检查最灵（`Record` 缺键、接口字段漏传这类单测看不出来） |
| 准备提交或交付 | 全量测试 + 类型检查 + 构建 + 行数检查 | 项目底线，不可跳过。构建覆盖类型检查看不见的静态资源与分包问题；行数检查测试与类型检查都抓不到。全量结果**以汇总行无 `Errors` 才算数**（判据见第 9 节） |
| 引入新文件或改动文件较多 | 加跑**改动文件**的 lint | 全量 lint 会被仓库既有报警淹没，信号被稀释 |
| 影响用户可见的输出（UI / 控制台 / 日志格式） | **必须真跑一次并看结果**，优先级排在上面全部之前 | 见下 |

**有一类 bug 静态检查抓不到：「渲染出来不对」**。真实案例——把 `.` 当背景在终端显示成一片圆点、拿字母当像素字符、中文按 1 列算导致信息栏错列：单测与类型检查全绿，用户看到的是一屏乱码。

配套两条实操：

- 起临时进程、截图这类重动作**只在最后一轮做一次**；启动前查端口占用，验证完务必关掉。
- 临时验证要和用户正在跑的实例**错开**：备用端口 + 临时数据目录，别动对方进程与数据；完事清理误建的目录与数据文件。

## 9. 测试

- 单测放**被测文件同目录**（`*.test.ts`），不集中放——测试与被测代码一起移动才不会漂。
- 新增核心逻辑时补同目录测试；UI 组件暂不强求。
- **测试环境按用例自身需要选，不要一律吃默认的重环境**：很多栈的测试默认跑在浏览器模拟环境里，那份开销远大于纯逻辑用例本体。纯逻辑测试（工具函数、纯数学/几何、协议解析、纯状态流转、数据结构）指定轻量环境；确实摸到 DOM / 窗口 / 本地存储 / 渲染 API（画布、尺寸观察器）的才保留重环境。
  - ⚠️ 判据看的是**用例自身**，不是被测源码——源码可能间接摸浏览器 API。改完必须真跑一遍确认，炸了就退回默认。降级环境是省时间，不是省可靠性。
- 需要打桩的场景：状态管理用「注入活跃实例」的官方写法；时间相关用假定时器；浏览器/网络 API（WebSocket、scroll、matchMedia）用 stub global。
- **UI 改动的浏览器实测套路**：原生拖放与复杂渲染容器内的对象命中需要合成事件才能测（对目标容器合成 `contextmenu`/`dragover`/`drop`，坐标 = 容器 rect + 元素中心；被遮挡的按钮可程序化 `el.click()`）。
- 写进 CHANGELOG 的「实测用例数」必须来自**完整的一次运行**。如果运行环境会静默少跑文件（沙箱权限报错但汇总仍显示通过），判据是：汇总行出现 `Errors` 即视为本次不可信，需重定向临时目录后多轮全量 + 补跑，直到逐文件列表与磁盘上的测试文件清单比对一致；若这种现象反复出现，**改用文件串行模式**（慢一些但一次跑全）比反复重跑更快收敛。
- 正因为全量结果可能不可信，第 8 节才把「默认跑受影响的测试」写成硬约束：日常绿灯不等于把关做过。
